## 一、简历写法（按篇幅提供两版，可直接复用）

### 版本 A：一页简历精简版（推荐，高密度量化）

**面向工业现场的防变砖 IAP 固件升级系统（SafeBoot-F1）** | 个人独立开发 | STM32F103C8T6 / 裸机 C / Python
- **架构与分区**：在 64 KB 片内 Flash 上无外部存储完成 **8 KB Boot + 24 KB App + 24 KB Slot + 2 KB 双页 Meta + 4 KB WAL 暂存**规划；纯寄存器直写 FPEC/USART1/IWDG（零 HAL 依赖），Bootloader 体积仅 **4,784 B**（58.4% 预算），驱动层在 `0x08002000` 设立 Boot 区硬写保护线。
- **掉电安全与自动回滚**：设计 **先备后主双页 Meta**（32 位递增 `seq` + CRC16）与 **WAL 预写日志双暂存页 A↔B 交换机制**，确保搬运任意微秒掉电可续搬且 Slot 自动留存旧版备份；结合 2 s IWDG 看门狗实现 `STATE_TESTING` 试运行，新固件未自检 Commit 连续复位 3 次后自动回滚。
- **可靠通信与续传**：实现 `0xAA55` 二进制分包协议（128 B/包，分包 CRC16 + 64 B 半字节查表 CRC32），支持重复 `seq` 幂等应答、乱序拦截与 **1 KB 页边界断点续传**；配套零依赖 Python 串口/SIL 双模上位机升级器。
- **全栈验证闭环**：搭建 PC 端 NOR Flash 物理仿真与故障注入框架（**1,167 项断言全通过**，穷举 93 步擦写半页撕裂掉电 100% 续搬，并提前捕获修复 WAL 第 0 页掉电边界缺陷）；完成 SIL 管道 4 场景对打与 STM32F103 真板 5 项实测（9600 bps 有效吞吐率 80.6%，死锁故障固件 3 次看门狗复位自动回滚）。

### 版本 B：详细 STAR 面试/作品集描述版

- **背景与痛点（Situation / Task）**：工业现场 MCU 远程串口/RS-485 升级面临三大“变砖”风险——① 下载或搬运中途意外断电导致固件残缺；② 误刷死循环/HardFault 坏固件导致设备失联无法再进 Bootloader；③ 仅 64 KB 片内 Flash 空间紧张，既放不下 HAL 库膨胀体积，又没有第三块 24 KB 分区做传统冗余备份。
- **核心设计（Action）**：
  1. **极致精简的寄存器级驱动与 6 步安全跳转**：直写 FPEC/RCC/USART1/IWDG 寄存器，使用 256 B 中断环形缓冲 + `USART_SR_TC` 防 RS-485 末字节截断；跳转 App 前依次执行栈顶/复位向量校验、关全局中断、关 SysTick、RCC 外设复位、清空 NVIC 使能/挂起位、切 `SCB->VTOR` 与 `MSP`。
  2. **双页先备后主 Meta + WAL 原子交换状态机**：通过主备双页（`0x0800E000/E400`）持久化 56 B 状态记录；利用 3 KB 预留页作 WAL 暂存（`OLD`/`NEW`/`TAG`），以 1 KB 为粒度原地互换 App 与 Slot，交换完成即自然形成 Golden Backup。
  3. **分包幂等与页对齐断点续传**：每满 8 包（1 KB 页边界）持久化 `dl_done_seq`，断电重连从页首续传并自动擦除半页残留，避免高频擦写 Meta 磨损 Flash。
  4. **PC 单元测试 → SIL 管道仿真 → 真板实测三级验证**：用模拟 NOR 物理特性 + 逐操作撕裂注入做 PC 白盒测试，再通过二进制管道 SIL 仿真器验证协议与状态机闭环，最后上 STM32F103C8T6 真板实测验证。
- **量化成果（Result）**：
  - Keil ARMCC V5.06 全 4 目标 **0 Error / 0 Warning**，Bootloader 仅占 **4,784 B**；
  - PC 单元测试 **1,167 / 1,167 通过**（含 93/93 步 WAL 撕裂掉电穷举与连续双次掉电恢复）；
  - 真板实测 3,824 B 固件 4.94 s 零重传下发，第 11 包断链续传精准命中 `seq=8`（耗时降至 3.61 s），刷入 `APP_VARIANT=99` 死锁固件后硬件 IWDG 复位 3 次自动恢复旧版并上报 `ROLLBACK_WDOG`。

## 二、五大核心技术亮点（面试可重点展开）

1. **在 64 KB 资源极限下实现“免第三分区”的原子互换（WAL Swap）**
   - 传统双槽回滚要么直接覆盖 App（覆盖途中掉电必变砖），要么需要外挂 SPI Flash。本项目仅借用 3 KB 内部预留页做 Write-Ahead Log（先备份旧/新页 → 写 `TAG` 事务提交点 → 再覆写目标页 → 更新进度），把“24 KB 整体拷贝的掉电窗口”压缩为**零风险的 1 KB 原子事务**。
2. **用“穷举故障注入”倒逼出真实边界 Bug（面试极加分！）**
   - 自己写带“NOR 只能 1→0 + 半页撕裂”规则的 Flash 模拟器，穷举 6 页交换全部 93 次 Flash 操作，直接抓出了**第 0 页 WAL TAG 落盘但 `swap_page_idx` 尚未递增时掉电**导致重启误校验 Slot 的隐蔽 Bug——这种靠手工拔电源几乎不可能复现的微秒级竞态，被自动化故障注入一击命中并根治。
3. **半字节查表法 CRC32（64 B 换 1,024 B）**
   - 针对 8 KB Bootloader 的空间约束，放弃 256 项全表（1 KB），改用 16 项 Nibble 查表法，仅占 64 B Flash、0 B RAM，72 MHz 下算完 24 KB 固件耗时不到 4 ms，且与 Python `zlib.crc32` 逐比特兼容。
4. **兼顾工业 RS-485 现场细节**
   - `bsp_uart1_write()` 在拉低 `PA8`（DE）前严格轮询 `USART_SR_TC`（而非 `TXE`），避免末字节停止位截断；协议层针对工业噪声设计前导字节抗干扰、坏 CRC16 静默丢弃、重复 `seq` 幂等应答（绝不重复擦写 Flash）。
5. **固件与 PC 验证架构解耦（同一份 C 代码跑三端）**
   - `boot_meta.c` 与 `iap_proto.c` 仅依赖抽象的 `bsp_flash.h` 接口，不做硬件寄存器耦合，使得同一份中间件源码无需修改即可同时编译进 **Keil STM32 真板**、**PC 白盒单元测试** 和 **PC SIL 管道仿真器**。

## 三、面试官高频深挖 10 问与参考应答

### Q1：Bootloader 跳转到 App 为什么需要“6 步清理”，漏掉某一步会有什么后果？
- **要点**：
  1. 先校验 `MSP`（落在 20 KB SRAM 内且 4 字节对齐）与 `Reset_Handler`（落在 `0x08002000~0x08007FFF` 且 bit0=1 为 Thumb），防止跳进空白 `0xFFFFFFFF` 引发 HardFault；
  2. `__disable_irq()` 防止切 VTOR/栈指针过程中响应中断；
  3. 停 `SysTick` 并通过 `RCC->APB2RSTR/APB1RSTR` 复位 USART1/TIM2/TIM3，防止外设遗留中断在 App 初始化前触发；
  4. 清空 `NVIC->ICER[0..2]` 与 `NVIC->ICPR[0..2]`，消除残留挂起中断；
  5. 设 `SCB->VTOR = 0x08002000` + `__DSB(); __ISB();` + `__set_MSP(sp)`（并且 App 的 `main()` 首行再次重设 `SCB->VTOR`，防止 `SystemInit()` 将其覆盖回 `0x08000000`）；
  6. 开中断并跳入 `Reset_Handler`。

### Q2：如果 App 运行起来后没有重设 `SCB->VTOR` 会怎样？
- **要点**：ST 官方 `system_stm32f10x.c` 里的 `SystemInit()` 默认会把 `SCB->VTOR` 设成 `FLASH_BASE | VECT_TAB_OFFSET`（默认 `0x08000000`）。如果不改 `VECT_TAB_OFFSET` 或不在 `app_main()` 首行重设 `SCB->VTOR = 0x08002000`，一旦 App 触发 `SysTick_Handler` 或 `USART1_IRQHandler`，CPU 会跳回 Bootloader 的中断向量表执行，立刻跑飞或死机。

### Q3：为什么双页 Meta 要“先写备页，校验成功后再写主页”？如果写主页写到一半掉电怎么办？
- **要点**：任何时刻只破坏一页，另一页永远保持完整合法记录。如果写完备页（`seq = N+1`）校验通过后，写主页时掉电导致主页撕裂（CRC16 错），重启时 `boot_meta_load()` 发现主页无效而备页有效，自动使用备页 `seq = N+1`；如果主页没坏仍是旧的 `seq = N`，比较 `seq`（用有符号差 `(int32_t)(a - b) > 0` 兼容 32 位回绕）后依然选中更新的备页 `seq = N+1`。

### Q4：WAL 交换过程中，哪几个时刻掉电最危险？你是怎么保证不丢数据的？
- **要点**：最危险的是**阶段 B 正在擦除或重写 `App[i]` / `Slot[i]` 的瞬间掉电**。因为进入阶段 B 前已经把 `App[i]` 和 `Slot[i]` 完整拷入 `WAL_SCRATCH_OLD/NEW` 并写了 `WAL_TAG = 0x53570000 | i`，重启后检测到 `TAG` 命中当前页号 `i`，就跳过阶段 A 直接重刷阶段 B，无论掉电多少次都能恢复。
- **追问加分**：顺带讲出我们在 PC 93 步穷举测试中发现的**第 0 页 WAL TAG 边界 Bug**（`swap_page_idx == 0` 但第 0 页 `TAG` 已生效时的续搬逻辑修复）。

### Q5：为什么下载阶段不在每收到 1 包（128 B）就更新一次 Meta 的 `dl_done_seq`，而是每 8 包（1 KB）存一次？
- **要点**：STM32F103 片内 Flash 页大小是 1 KB，典型擦写寿命约 1 万次。如果每 128 B 更新一次双页 Meta，传 24 KB 要擦写 Meta 192×2 = 384 次，既拖慢升级速度又加速 Flash 磨损；按 1 KB 页边界持久化，传 24 KB 仅写 24 次 Meta，且续传时一定从页首开始（`offset % 1024 == 0`），正好直接整页擦除上一次中断留下的半页脏数据，满足 NOR Flash “写前必擦”的物理约束。

### Q6：如何防止刷入的“坏固件”本身能喂狗、或者死在初始化阶段？
- **要点**：
  - 死在初始化/死循环/HardFault：Bootloader 跳转前已启动 **2 s 硬件 IWDG**（且 LSI 独立时钟驱动，一旦开启软件无法关闭），App 必须在稳定跑满 1000 ms 完成基础自检后才调用 `boot_meta_commit_app()`；否则 2 s 复位，连续 3 次（`try_cnt >= 3`）Bootloader 强制进入 `BOOT_STATE_ROLLBACK` 从 Slot 刷回旧版。
  - 若升级到更复杂工业场景，还可在 Commit 前加入外设自检（如 ADC 采样正常、关键传感器通信握手成功、收到主站首条心跳后再 Commit）。

### Q7：如果新固件在 `CMD_DATA` 阶段遇到串口丢包或应答丢失，协议怎么处理？
- **要点**：上位机超时重传同一 `seq`。若设备端上次没收到（或 CRC16 错被静默丢弃），则正常写入；若设备端上次已写入 Flash 但 ACK 在回传路上丢了，设备端收到 `seq < ram_done_seq` 时走**幂等分支**——直接返回 `OK + ram_done_seq`，**绝不重复对同一地址二次编程**（NOR Flash 重复写会触发编程错误或位损坏）。

### Q8：为什么要自己直写 FPEC 寄存器并在驱动层加 `0x08002000` 写保护线？
- **要点**：① Bootloader 只有 8 KB 预算，直写 FPEC 寄存器仅 186 行代码、占用极小且可控性极高；② 任何指针算错或恶意指令若擦除了 `0x08000000~0x08001FFF`，板子就会永久变砖（只能现场拆壳接 ST-Link）。在 `bsp_flash_erase_page()` 和 `bsp_flash_program()` 入口硬编码 `addr < 0x08002000` 拦截，从底层杜绝软件越界自毁（量产还可叠加 STM32 Option Bytes 写保护 WP0/WP1 实现硬件级锁死）。

### Q9：你的 STM32F103 Flash 操作时中断会受什么影响？
- **要点**：STM32F103 为单 Bank Flash，执行 FPEC 页擦除（约 20~40 ms）或半字编程期间，CPU 若从 Flash 取指（包括响应存放在 Flash 的中断向量/ISR）会被硬件自动暂停等待（Flash Stall）直到擦写完成。在 9600 bps 下 1 字节耗时 1.04 ms，我们协议采用**半双工一问一答（Stop-and-Wait）**——上位机发完 128 B 帧后必须等待设备回 ACK 才会发下一帧，因此设备擦写 Flash 时串口线上无后续字节涌入，完全避免了 `USART_SR_ORE` 溢出丢字节。

### Q10：为什么还要花精力写 PC 单元测试和 SIL 仿真器，不直接上板子调试？
- **要点**：① 真板上你无法精确在“擦除第 3 页第 512 字节的微秒瞬间”拔电源，而在 PC 仿真桩里 1 秒就能把 93 个 Flash 操作点的撕裂掉电全部穷举完；② SIL 管道把真实 `boot_meta.c` / `iap_proto.c` 与 `upgrader.py` 串起来做自动化回归，每次改代码 3 秒就能跑完上千断言 + 全流程升级/回滚，上真板时一次烧录 5 项全过，大幅降低硬件联调成本。
